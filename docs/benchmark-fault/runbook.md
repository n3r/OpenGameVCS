# Benchmark and fault-harness runbook

This runbook operates the OGVCS-005 `1.0.0-rc.1` candidate. The normative
authority is [`spec/benchmark-fault/v1`](../../spec/benchmark-fault/v1), the
reference runtime is
[`foundation/benchmark-fault-harness`](../../foundation/benchmark-fault-harness),
and the security/compatibility decision is [ADR-0014](../../adr/0014-benchmark-fault-harness-contract-v1.md).

## Safety boundary

The ordinary commands in this document are bounded and unprivileged. They do
not execute the OGVCS-002 one-million-entry tree or logical-1-TiB manifest
campaigns. Those two jobs require separate final-R0 authorization and are not
implied by `smoke`, `presubmit`, `nightly`, package validation, or release-plan
generation.

Fault injection is test-only. Never expose the benchmark driver or a fault hook
on a production service. A product adapter may arm faults only after successful
`ogvcs.benchmark-fault-driver.test@1` negotiation and lifecycle start in an
authenticated isolated test mode.

Privileged host network shaping is release-only. Run it in a disposable,
isolated worker with a reviewed adapter and no production credentials or
production network path. The normal local, presubmit, and nightly profiles do
not require root, administrator, containers, or host network mutation.

## Prerequisites

- Node.js 22 or later and npm with the repository lockfile installed by
  `npm ci --ignore-scripts --no-audit --no-fund`.
- A clean output directory; result publication uses create-only files and an
  atomic final directory rename.
- Enough local space for the selected synthetic profile and retained evidence.
- For an external implementation, an executable adapter implementing the
  registered test-driver protocol.

Verify the candidate authority before a run:

```sh
node spec/benchmark-fault/v1/source/generate.mjs --check
node spec/benchmark-fault/v1/validate-spec.mjs
npm run test:benchmark:spec
```

The validator checks all generated bytes, task/fault/profile coverage, error
parity, threshold requirement IDs, and exact OGVCS-001/002/003/004/041
predecessor pins, including the fixture profile set.

## Choose a profile

| Profile | Purpose | Timed samples | Fault proof | Network control |
|---|---|---:|---|---|
| `local-smoke` | Developer feedback and package proof | 110 | Separate 36-row proof | Loopback simulation |
| `presubmit` | Required bounded change gate | 1,320 | Yes | Loopback and 20 ms simulation |
| `nightly` | Complete unprivileged matrix | 8,800 | Yes | All four simulated profiles |
| `release` | Candidate release matrix | 33,000 | Yes | Simulation plus isolated privileged adapter |

All profiles cover the five `code-heavy`, `global-studio`, `large-binary`,
`unity-like`, and `unreal-like` corpora and all eleven task families. Planning a
profile never executes it:

```sh
node foundation/benchmark-fault-harness/bin/ogvcs-benchmark.mjs plan \
  --contract spec/benchmark-fault/v1 \
  --output /tmp/ogvcs-benchmark-plan.json
```

Inspect the plan before scheduling nightly or release work. A release plan must
declare 33,000 timed samples, twelve fault points, and `privileged: true`.

## Run a bounded local result

Use a new output path and record an explicit seed:

```sh
node foundation/benchmark-fault-harness/bin/ogvcs-benchmark.mjs smoke \
  --contract spec/benchmark-fault/v1 \
  --profile local-smoke \
  --seed operator-reviewed-seed \
  --operator local-review \
  --classification synthetic \
  --output artifacts/benchmark-fault-result
```

The command creates a temporary workspace unless `--workspace` is explicitly
provided. It materializes only bounded synthetic fixtures. A successful CLI
result reports the sample count, conformance counts, bundle digest, contract
manifest, and final status.

For deterministic retained CI evidence with fixed measurement clocks and no
simulated wall delay, use:

```sh
node tools/benchmark-fault-conformance-report.mjs \
  --output artifacts/benchmark-fault-source \
  --profile presubmit
```

That tool accepts only `local-smoke`, `presubmit`, or `nightly`; it refuses the
privileged release profile. The retained `report.json` sets
`exactScaleExecuted: false`.

## Run fault and checker proofs

Execute all registered durability boundaries and intentionally broken-service
checks without a performance matrix:

```sh
node foundation/benchmark-fault-harness/bin/ogvcs-benchmark.mjs faults \
  --contract spec/benchmark-fault/v1 \
  --seed reviewed-fault-seed \
  --output /tmp/ogvcs-fault-proof.json
```

A passing proof contains 36 boundary/action rows and seven detected broken
service modes. Investigate any unobserved injection, task that incorrectly
claims success, failed post-restart invariant, or broken mode that the checker
misses. Do not waive a correctness failure to preserve a latency result.

The ordered fault schedule is a pure function of the seed and registered fault
IDs. Repeating the same contract and seed must produce the same schedule digest.
A different contract manifest is a different authority and requires a new
comparison baseline.

## Verify a published bundle

Always verify before reading a bundle as evidence:

```sh
node foundation/benchmark-fault-harness/bin/ogvcs-benchmark.mjs verify \
  --contract spec/benchmark-fault/v1 \
  --bundle artifacts/benchmark-fault-result \
  --output /tmp/ogvcs-bundle-verification.json
```

Verification rejects links, unknown files, wrong lengths/digests, malformed or
oversized JSONL, inconsistent identities, invalid raw records, and forged
derived claims. It recomputes summaries, threshold evaluations, final status,
and the complete bundle digest from the authenticated raw inputs.

Successful publication includes:

- `result.json`: authority digests, profile, threshold authority, overhead,
  retention/redaction record, and generated reproduction template;
- `environments.jsonl`: one bounded environment record per executed lane;
- `samples.jsonl` and `summaries.jsonl`: raw measurement and calculation data;
- `evidence.json`: fault, intentionally broken service, and security/path
  negative-suite results;
- optional `conformance.json`; and
- `manifest.json`: the exact file inventory, lengths, SHA-256 values, and bundle
  digest.

Do not copy credentials, arbitrary shell commands, full protected paths,
partner names, or production data into public metadata. The public normalizer
accepts inert JSON data, removes credential-like fields, hashes declared
partner/operator identifiers, and applies a bounded expiry. Treat a rejected
redaction input as a failed publication, not a reason to bypass normalization.

## Compare two results

Comparison requires two already valid bundles:

```sh
node foundation/benchmark-fault-harness/bin/ogvcs-benchmark.mjs compare \
  --contract spec/benchmark-fault/v1 \
  --baseline artifacts/baseline/bundle \
  --candidate artifacts/candidate/bundle \
  --tolerance-ppm 50000 \
  --output /tmp/ogvcs-comparison.json
```

The comparator requires equivalent contract, workload, threshold, reference
environment, inventory, status, retry, byte, and correctness semantics.
Operator identity and capture time may differ. The threshold authority fixes
the maximum tolerance; `--tolerance-ppm` may make a review stricter but cannot
loosen that authenticated cap. The tolerance applies only to declared
comparable metrics; it cannot excuse an incomplete task, failed assertion,
threshold failure, or authority mismatch.

When reproducing a published result, retain both bundles and the comparison
record. AC-05 requires another operator, not merely a second invocation by the
publisher. Record the second operator's environment and review any difference
rather than editing the evidence to match.

## Offline package and three-OS proof

To reproduce the packaged closure locally:

```sh
node tools/run-packed-benchmark-fault-conformance.mjs \
  --output artifacts/benchmark-fault-packed \
  --profile local-smoke
```

The tool normalizes and hashes ten exact npm archives, installs them together
with npm offline and lifecycle scripts disabled, runs the installed CLI plan,
and publishes an installed-package retained report plus
`packed-evidence.json`. It uses a new private npm cache and does not contact a
registry.

The commit-pinned workflow `.github/workflows/benchmark-fault-harness.yml`
runs that proof on Ubuntu, macOS, and Windows. Its comparison job requires equal
contract, profile, semantic-result, and package-set digests:

```sh
node tools/compare-benchmark-fault-reports.mjs \
  artifacts/downloaded/benchmark-fault-Linux/packed-evidence.json \
  artifacts/downloaded/benchmark-fault-macOS/packed-evidence.json \
  artifacts/downloaded/benchmark-fault-Windows/packed-evidence.json
```

Do not declare platform parity from one local report. Retain the workflow run,
job, archive, and comparison identifiers in the evidence packet after the
commit-pinned hosted run completes.

## Threshold ownership and dashboards

The default candidate thresholds live at
`spec/benchmark-fault/v1/thresholds/default-v1.json`. Each row names a stable
PRD requirement, profile set, task selection, metric, operator, value,
minimum-sample count, and gate/warning severity. A product PRD adds or changes
its threshold through a versioned contract change; it does not patch harness
code or post-process a failing report into success.

Dashboards ingest only verified bundles. Index at least:

- contract, threshold, corpus, implementation, and environment authorities;
- profile, task, cache state, network state, and sample count;
- p50/p95/p99, median absolute deviation, failures, incompletes, retries, and
  measurement overhead;
- disk/network/logical/unique bytes and their ratios;
- threshold result linked to the owning requirement ID; and
- fault/checker/security outcomes as correctness signals separate from
  availability or latency.

Alert on any gate failure, missing raw artifact, manifest mismatch, exact
authority drift, unobserved fault, checker miss, or cross-platform semantic
difference. A warning threshold may trigger investigation without changing the
bundle's raw values.

## Privileged release execution

The repository workflow intentionally generates only a release plan. To run the
privileged lane, an authorized release operator must:

1. provision a disposable isolated worker with no production credentials or
   routes;
2. review and install an adapter exposing synchronous `apply(profile)` and
   `reset()` with `isolated: true`;
3. verify the exact contract, package, threshold, and implementation digests;
4. run the unprivileged matrix first;
5. execute the privileged network lane with cancellation and cleanup monitors;
6. require adapter reset and host teardown even after failure; and
7. retain the verified bundle, adapter identity, plan, logs, and operator review.

If isolation, privilege, cleanup, or adapter identity is uncertain, stop before
`apply`. Never silently substitute privileged results with simulation or label
simulation as reference-host network evidence.

## Troubleshooting

| Symptom/code | Action |
|---|---|
| `HARNESS_INPUT_INVALID` | Validate exact inert input shape, canonical integers, profile/task IDs, paths, and required arguments. |
| `HARNESS_LIMIT_EXCEEDED` | Reduce the bounded profile or raise a reviewed configured ceiling within the hard limit; do not disable accounting. |
| `HARNESS_NEGOTIATION_INCOMPATIBLE` | Compare driver/control profile, versions, capabilities, contract digest, and test-mode setting before enabling hooks. |
| `HARNESS_PROTOCOL_MALFORMED` | Inspect bounded stdout JSONL, message ordering, result/error consistency, trace limits, and unexpected stderr. |
| `HARNESS_DEADLINE_EXCEEDED` or `HARNESS_CANCELLED` | Confirm process-tree termination and controller rollback; rerun only with the same explicit seed and a reviewed deadline. |
| `HARNESS_CACHE_STATE_INVALID` | Inspect prepared and observed local/regional byte counters; replace the cache adapter rather than overriding the result. |
| `HARNESS_PRIVILEGE_REQUIRED` | Use an isolated approved adapter or select an unprivileged profile. |
| `HARNESS_FAULT_INVARIANT_FAILED` | Preserve the failed evidence and service state; treat as a release-blocking correctness defect. |
| `HARNESS_THRESHOLD_FAILED` | Identify the owning requirement and raw metric; do not edit the report or threshold in place. |
| `HARNESS_BUNDLE_INVALID` | Quarantine the bundle, verify exact file inventory/digests, and reproduce from the source run. |

For a deterministic mismatch, first compare contract manifest, fixture profile
set, seed digest, implementation commit digest, cache/network profile, task
inventory, threshold digest, and environment. Comparing latency across different
authorities is not a valid reproduction.

## Retention and rollback

Retain source and packed bundles for the period declared in `result.json` and
the hosted artifacts for the workflow retention period. Preserve failed
correctness/fault evidence until the owning defect is resolved. Public bundles
contain only synthetic or explicitly approved partner-derived classification;
partner-derived data requires the same redaction review before publication.

To withdraw a faulty harness candidate, remove it from release gates, disable
and remove test fault adapters, mark affected report manifests invalid for
promotion, and pin the prior accepted contract/threshold authority. Do not
rewrite or delete historical bundles to make them appear valid under a newer
contract.
